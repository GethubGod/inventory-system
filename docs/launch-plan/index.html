5. UI revamp approach

You asked whether to hand the whole UI to one agent or decide the revamp here with mockups first. Four options, one recommendation.

A. One agent sweeps everything freehand

One long session opens each screen and "makes it consistent".

Fast to start, slow to finish. This is how the current drift happened. Without a written contract the agent's taste changes as its context fills, and screen 60 does not match screen 5. One agent also means serial work and a 600k chat.

B. Contract first, then parallel sweeps (recommended)

One short session produces a style guide: tokens, seven primitives, and three variants of the two things you must choose (header, tab bar). You pick. The primitives are built once. Then four agents sweep four areas in parallel, each forbidden from writing colours or sizes directly, enforced by lint.

Why it wins. Consistency is enforced by a rule, not by taste. Parallel work is safe because each agent owns different folders. Your involvement is one 45 minute pick, not a review of 72 screens.

C. Full redesign, every screen mocked up

Mock all 72 routes in HTML, iterate with you, then build.

Too slow and not needed. You already confirmed the employee design and colourway. Most manager screens have the right structure and only need the same chrome. Save full mockups for screens that are genuinely broken, which is the auth set.

D. Ship as is, fix after launch

Launch with the current look, revamp in 2.4.

Reasonable only if App Store timing matters more than first impressions. The auth screens are the weakest and are the first thing a reviewer sees. If you choose this, do at least the auth set and the tab bar unification.

6. How to operate: issues, PRs, chats and agents

The honest answer to "GitHub issues, PRs, or something else": use issues as the ledger, PRs as the unit of delivery, and keep every chat small by never letting a chat be the place where state lives.

A GitHub issue is a numbered ticket in the repo with a title, a description and a comment thread. A milestone groups issues under one goal, here "App Store 2.3". A pull request (PR) is a proposed set of commits from a branch, reviewed and then merged. A worktree is a second checkout of the repo in its own folder on its own branch, so several agents can edit at once without stepping on each other. The context window is everything a chat has read so far; the model re-reads all of it on every message. An orchestrator is a chat that plans, dispatches and reviews but does not edit files itself.

Why issues, concretely

  • A new chat can load its whole job in 2,000 tokens. gh issue view 41 returns the description, the acceptance criteria and every status comment. Today the same information is scattered across a 600k chat, three handback markdown files and your memory.
  • Parallel agents cannot collide. Each issue names its branch, its worktree and the folders it may touch. Two issues never own the same folder.
  • You review once per deliverable. A PR says "Closes #41", the issue closes on merge, the milestone shows what remains. No status meeting in chat.
  • Handoff becomes a comment, not a document. Every chat ends by posting done / remaining / validation on the issue. The next chat starts by reading it.
  • It is searchable in six months. "Why did we remove hard caps?" is an issue with a decision comment, not a chat you cannot find.

What it is not: it is not a board to look impressive. If you never open the GitHub UI, it still works, because agents read and write it through gh.

Answer to "one main orchestrator or many small chats". Both, with a hard rule: the orchestrator stays thin. It reads summaries and diffs, never whole files, and it is retired at the end of every phase. Workers are the small chats. A subagent's report comes back into the orchestrator's context, so ask workers to write their evidence to the issue and return only a five line summary. That single rule is what keeps the orchestrator under 100k tokens across a phase.

Rules that keep it functional

  • One deliverable per issue, one issue per PR, no stacked PRs. You merge out of order.
  • Every issue states: goal, acceptance criteria, owned folders, validation commands, and whether it needs a decision from you (label needs-david).

  • Cross-vendor review is opt-in and named per PR: which reviewer, which commit.
  • Worktrees are removed when the PR merges. A cleanup pass lists candidates with dirty status and waits for your go.

7. Context windows and cost, explained

Yes, several small chats are cheaper than one 600k chat, and the reason is mechanical, not stylistic.

How a chat is billed. Every message you send makes the model re-read the entire conversation so far. If the chat holds 600k tokens, each reply costs 600k input tokens plus the reply. Prompt caching makes re-reading recent context much cheaper, but the cache expires after idle time (this session uses a one hour cache), and after that the whole prefix is read again at full price. Whether you pay per token or through a plan's usage limit, the same tokens are consumed.
Context size when you send one messageInput cost per message, cache warmInput cost per message, cache cold (after idle)What it feels like
50k tokens (a fresh worker on one issue)about $0.01about $0.50Fast, precise, nothing stale
200k tokens (a healthy orchestrator at end of phase)about $0.05about $2.00Fine
600k tokens (the chats you have been running)about $0.15about $6.00Every message after a coffee break costs $6 before the model writes a word; summaries drop details; the model argues with facts from 300 messages ago

Rates used: Claude Fable 5.1 at $10 per million input tokens, cache reads at $0.25 per million, from the current API price list. Output tokens are extra ($50 per million) and are the same in either model of working. The figures are per message, so multiply by the number of messages in a session.

Where the savings actually come from

  • Workers carry only their issue. A worker that reads five files and an issue runs at 30k to 80k tokens for its whole life. Ten such workers cost less than one 600k chat that lasts a day, and they run in parallel.
  • The orchestrator never reads code. Diffs and summaries only. That is what keeps it under 100k to 200k for a phase.
  • Evidence goes to files and issues, not to context. Screenshots, logs and route matrices are written to disk and linked. A subagent returning a 20k token report into the orchestrator defeats the purpose.
  • Retire chats on purpose. End a chat when its issue closes or its phase ends. The handoff comment costs 300 tokens; the next chat loads it instead of 600k of history.
  • Model routing. Your table already says it: Fable for orchestration, review and design; Opus for implementation; Sonnet for mechanical sweeps. Sonnet at $2 per million input is a fifth of Fable for the hex colour replacement job, and just as good at it.

Quality goes the same direction. The defects fixed on this branch (stale data after account switch, a second modal over the first) are the kind that a fresh, focused chat catches and a tired 600k chat talks past.

D. Glossary

EAS
Expo Application Services. The cloud that builds the signed iOS binary and holds production environment variables such as the Supabase key.
Publishable key versus legacy anon key
Two forms of the public Supabase API key. The edge functions in this project accept only the newer publishable form; the legacy form gets 401.
TestFlight
Apple's way to install a pre-release build on a real iPhone. Required for push, microphone and SMS checks that the simulator cannot do.
App Store Connect
Apple's web console where version metadata, privacy answers, screenshots and the reviewer account are entered before submission.
Disposable local stack
A full Supabase copy running in Docker on your Mac with the production schema and fixture data. Writes there touch nothing real.
Route
One screen file under app/. Expo Router turns the file path into a navigable address.
Design token
A named value such as colors.primary or spacing.md that screens reference instead of writing the raw number. Change the token, every screen follows.
Primitive
A small shared component (button, header, chip) that every screen composes instead of drawing its own.
Lint rule
An automated check that fails the build when code breaks a convention, here "no raw colours outside the theme".
Prompt cache
The API's short-term memory of a conversation prefix. A warm cache makes re-reading cheap; it expires after idle time.
Subagent
A child chat launched by an orchestrator for one task. Its final report is added to the orchestrator's context, so it should be short.
Cross-vendor review
Having a Codex model review Claude's work or the reverse, so a second model family reads the same spec.
