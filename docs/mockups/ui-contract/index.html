Smelter UI contract

Tokens, primitives and two choices for your approval. Once you pick a header variant and a tab bar variant, this file becomes the ticket for the primitives build (#32) and the four sweeps (#33 to #36). Every screen in the app will be rebuilt from these pieces only, and a lint rule will refuse anything else.

How to approve

Two picks, then a comment on GitHub issue #31. Everything else is fixed by decisions you already made.

  1. Header. Pick H1, H2 or H3 in section 3. Recommended: H1.
  2. Tab bar labels. Pick T1, T2 or T3 in section 4. The floating pill itself is decided (decision 7). Recommended: T1.
  3. Use the switches in section 5 to see any combination on the four reference screens.
  4. Comment on #31, for example: H1 + T1, go. Add changes as bullets if you want anything different.
What this file is and is not. It is a rendered contract in plain HTML, not the app. The reference screens are close likenesses, not pixel copies. The point is that every colour, size, radius and component you see here is the complete list the app is allowed to use after the sweeps. If a screen needs something not on this list, the sweep agent files an issue instead of inventing it.

6. Rules for the sweep agents

These go verbatim into issues #33 to #36. They are what stops the drift from coming back.

  1. No literals. No hex colour, rgba, numeric fontSize, numeric borderRadius, or fontWeight other than 400, 600, 700 outside src/theme and src/components/ui. The ESLint rule from #32 fails on any of these.
  2. No raw hosts. No ActivityIndicator, Modal, or hand-drawn back button. Use Loading, Sheet, ScreenHeader.
  3. One primary per screen. One primary Button visible at a time. Everything else is secondary or small.
  4. Status colours are for StatusPill only. Never on a button, chip, or title.
  5. No behaviour change. A sweep changes how a screen looks, not what it does. If a behaviour bug is found, file an issue and keep going.
  6. Copy. No em-dashes, no emoji, short sentences.
  7. Evidence. Every PR carries a before and after screenshot for each screen from the pinned simulator, and the lint rule count for its folders reads zero.
  8. Ownership. A sweep touches only the folders listed in its issue. Shared components live in #32 and are changed there, never in a sweep.
  9. Missing piece. If a screen needs a component not in section 2, stop, file an issue against #32, and use the nearest existing primitive in the meantime.
